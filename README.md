# eval-harness

Statistically rigorous evaluation for LLM systems.

## The problem

Standard eval practice — running a variant against a few dozen examples and
declaring a winner from a p-value — routinely cannot detect the effects it
claims to find: at realistic sample sizes the minimum detectable effect is
often far larger than the improvement anyone is actually shipping (spec
§9.3). This library replaces that workflow with paired estimators, an
uncertainty measure on every number, and measured — not assumed — bias from
winner's-curse selection, uncorrected position effects, and testing many
variants at once.

## Measured findings

Each number below is read from a CSV in `validation/results/`, generated by
running the actual estimator/test on synthetic data with known ground truth
(10,000 replications, seeded).

- **Winner's curse.** k = 4 candidate variants share a true effect of 0.10;
  the empirical best's estimate averages 0.245 (more than double the truth),
  while a pre-designated candidate averages 0.10 (unbiased).
  [`winners_curse_reps10000.csv`](validation/results/winners_curse_reps10000.csv)
- **Counterbalancing.** An injected additive position bias of 0.15 is fully
  removed by the order-balanced reduction (measured bias −0.0002); naive
  pooling of the same judge calls carries 0.075 of it straight into the
  estimate.
  [`counterbalancing_reps10000.csv`](validation/results/counterbalancing_reps10000.csv)
- **Multiplicity cost.** Holm-adjusted power against a shared control, same
  per-contrast effect size, drops from 0.64 at k = 3 candidate variants to
  0.42 at k = 10.
  [`multiplicity_k3_reps10000.csv`](validation/results/multiplicity_k3_reps10000.csv),
  [`k5`](validation/results/multiplicity_k5_reps10000.csv),
  [`k10`](validation/results/multiplicity_k10_reps10000.csv)
- **Minimum detectable effect — analytic, not measured.** Connor's formula
  (spec §9.3): 50 items, binary pass/fail, 30% discordance, α = 0.05, power
  0.80 → MDE ≈ 0.21. A real 5-point improvement has roughly a 9% chance of
  reaching significance at that sample size.
- **Self-preference: naive vs. corrected.** A judge scoring its own model's
  responses shows a naive win-rate excess of 0.130; the cross-judge-corrected
  estimator isolates the self-preference component alone at 0.080 — the
  naive number overstates self-preference by 63%, with the rest attributable
  to a genuine quality difference the naive quantity doesn't control for.
  [`bias_self_preference_reps10000.csv`](validation/results/bias_self_preference_reps10000.csv)

## What the library does

`evalkit/stats/`, `evalkit/judge/`, `evalkit/bias/`, and `evalkit/runner/`
are implemented and validated; `evalkit/agreement/` is not yet built (see
Status).

### `stats/` — estimators, tests, intervals, power

- `engine.py` — the shared inference engine (spec §2): cluster percentile
  bootstrap CI, cluster sign-flip permutation test, analytic cluster-robust
  cross-check.
- `scenarios.py` — scenario front-ends (pairwise preference, scalar rubric,
  binary pass/fail; §3–§5) that run reduction + engine and emit the full
  report block (§10), including which CI is primary at the achieved cluster
  count and why.
- `reduction.py` — raw judgment rows → one paired item-level difference
  (§1.2), including order-balanced pairwise scoring.
- `mcnemar.py` — exact McNemar test, the classical cross-check for the
  binary singleton case (§5).
- `multiplicity.py` — Holm (FWER) and Benjamini–Hochberg (FDR) corrections
  (§6).
- `power.py` — analytic power/MDE formulas (§9.1) and a simulation-based
  power tool (§9.2) sharing the validation suite's generative code.
- `variance.py` — judge-noise and between-item variance components
  (σ²_J, σ²_B; §8).
- `coverage_evidence.py` — the measured coverage table backing the
  analytic-vs-bootstrap CI choice (spec §2.1/§2.3, DECISION D9).
- `simulate.py` — synthetic data generators shared by the validation suite
  and the power tool.

### `judge/` — LLM-as-judge prompts and strict parsing

- `prompts.py` — pairwise/scalar/binary judge prompts plus the generation
  prompt; `counterbalanced_pairwise_tasks` makes counterbalancing structural
  — both presentation orders are always built together under one `pair_id`,
  never in isolation.
- `parse.py` — verdict parsing that refuses to guess: a missing verdict,
  conflicting verdicts, a disallowed tie, or an out-of-scale score raises
  instead of being coerced to something plausible.
- `records.py` — the `docs/data-model.md` record types (`RunConfig`,
  `PlannedJudgeCall`, `ResponseJudgment`, `PairwiseJudgment`) with the
  data model's write-time constraints enforced at construction (pinned
  `judge_model`, presentation-terms verdicts, immutable `call_role`).

### `bias/` — judge systematic-error measurement (spec §14)

Every estimator reduces judgment records to an item-level vector and hands
it to the same `stats/` engine unchanged — no separate resampling code.

- `position.py` — `position_bias`, the additive marginal position effect
  (§14.2).
- `verbosity.py` — `verbosity_association` (observational, named as an
  association per the F14 naming rule, never a bias) and
  `verbosity_bias_controlled` (the controlled length-manipulation study,
  §14.3).
- `self_preference.py` — `self_preference_bias`, the cross-judge contrast
  that separates genuine quality from self-preference (§14.4).

### `runner/` — executing a run against real models

- `client.py` — a `ModelClient` protocol; the runner is client-agnostic, so
  tests plug in a mock and production code plugs in a real one, with no
  network calls either way.
- `cache.py` / `store.py` — a disk-backed response cache and an append-only
  resumable record store, so an interrupted run resumes rather than
  restarts.
- `retry.py` / `concurrency.py` — retry with backoff on rate limits, and
  bounded concurrency via a thread pool.
- `generate.py` / `judging.py` — response generation and judge execution,
  including `call_role` (primary/replicate) labeling at request-creation
  time (spec §12 gap 9).
- `pairwise_plan.py` — the DECISION D4 item-level replicate draw, the
  `PlannedJudgeCall` request plan written before any call is made, and the
  gate that joins realized records back to that plan.
- `plan.py` — `dry_run`: predicted billable calls and cost before spending
  anything.

### Applied: a real study, not just a library

`docs/position-bias-study.md` is a full pre-registered design — judges,
item bank, replicate subset, sample-size/MDE planning, a simulation gate,
a falsification checklist — for measuring whether Anthropic's judge models
prefer the response shown first. `study/` carries it from design toward an
executable run: a seeded, reproducible prompt sample from a public
benchmark (`build_prompt_set.py`), a launch gate that runs synthetic
judgments through the *real* reduction and engine to check for pipeline
power loss before spending API budget (`simulation_gate.py`), and a
six-phase driver (`run_study.py`: generate, check-arms, plan, dry-run,
judge, gate) where every money-spending phase prints its predicted cost and
requires an explicit `--confirm`. The study itself has not been run against
the live API yet (see Status).

## Known limitations

- **Percentile bootstrap under-covers at small cluster counts.** At C = 20
  clusters, measured 95%-nominal coverage is 92.5% (bootstrap) vs. 94.9%
  (analytic); at C = 30, 93.5% vs. 95.0%; the gap closes by C = 50, 94.2%
  vs. 95.1%.
  [`coverage_reps10000.csv`](validation/results/coverage_reps10000.csv)
  This is why the analytic cluster-robust interval, not the bootstrap, is
  now the *primary* CI below C = 50 (spec §2.1/§2.3, DECISION D9) — the
  bootstrap is still always computed and reported, just not headlined.
- **One-sided tests carry level error outside the exchangeability null.**
  The sign-flip test is exact under the stated symmetry null; against the
  weaker mean-zero-but-asymmetric null (§2.2, F12), the measured one-sided
  rejection rate reaches 9.1% at C = 20 against nominal 5% when rejecting
  into the long tail (2.5% in the conservative direction on the same cell).
  Two-sided rates on the same grid stay within 5.4–6.8%.
  [`null_robustness_probes_reps10000.csv`](validation/results/null_robustness_probes_reps10000.csv)
- **The exact binary (McNemar) test is conservative, and that costs power.**
  Measured true rejection rate under the null is 2.79% (ψ = 0.3) and 2.08%
  (ψ = 0.1) against nominal 5%.
  [`false_positive_rate_reps10000.csv`](validation/results/false_positive_rate_reps10000.csv)
  The Connor power formula assumes the nominal level is achieved; simulated
  power on the binary/Connor cell falls 3.63 points short of the formula's
  prediction as a direct consequence (73.65% analytic vs. 70.02%
  simulated).
  [`power_agreement_reps10000.csv`](validation/results/power_agreement_reps10000.csv)
  Mid-p McNemar would be better calibrated on average but is not
  conservative on any single dataset, so it isn't used (F5).

## Validation

Correctness is established by simulation, not unit tests: every estimator,
test, and interval ships with a study in `validation/` that runs the actual
pipeline on synthetic data with known ground truth and checks coverage,
false-positive rate, power agreement, or an exact identity (spec §11).

1. CI coverage — bootstrap and analytic, across scalar/binary/preference
   outcomes, clustered and unclustered.
2. False positive rate — sign-flip test and McNemar cross-check under true
   nulls.
3. Power agreement — simulated vs. analytic power on the formulas' home
   turf.
4. Identities — sign-flip ≡ exact McNemar; cluster-robust SE ≡ paired t at
   singleton clusters; counterbalancing removes an injected position
   effect.
5. Variance components — σ²_J, σ²_B recover known simulation truth,
   including the truncation-at-zero regime.
6. Multiplicity — Holm FWER / BH FDR control under complete and partial
   nulls, k ∈ {3, 5, 10}.
7. Winner's curse — selection bias of the empirical best of k, measured.
8. Null-robustness probes — sign-flip behavior outside the exchangeability
   null (recorded, not build-failing).
9. Bias estimator recovery — position, verbosity (observational association
   plus the controlled-manipulation check), and self-preference (naive vs.
   cross-judge-corrected), at the same clustered grid as coverage.

Results are published to `validation/results/*.csv` on every run; the
numbers in this document are read from those files, not restated by hand
elsewhere.

Reproduce:

```
pytest -m validation                          # smoke scale, 200 reps, seconds
pytest -m validation --validation-reps=10000  # full scale, ~10 minutes, machine-dependent
```

Every stochastic function takes an explicit seed (spec §0); the same seed
and inputs reproduce the same numbers bit-for-bit — there is no global
random state.
